### 为什么插件层能覆盖 app 的文案

DSH 的文案走它自己的 locale 服务。查过源码（`dsh-client-locale`）：**只有 `register`，没有覆盖入口**，
且同一命名空间+语言重复注册会直接抛错。但 `register` 存进 `dicts` 的是字典对象的**引用**——
所以插件拿到那个对象改属性即可，等效于"官方覆盖"，且不碰磁盘文件。

### 术语表（`TERM_MAP`）为什么比逐条列 key 好

比"列出 25 个 key 逐个改"耐升级：DSH 新增的含「工作区」的文案会自动跟上。
长词在前（`会话工作区` 先于 `工作区`），避免"浏览会话工作区的文件"变成"浏览会话投研空间的文件"。
精确覆盖（`TEXT_OVERRIDES`）在术语替换**之后**执行，可用来反悔个别词条。

### 安全边界（脚本里已固化）

- **绝不改** `DESKTOP_PRODUCT_NAME` / `app.setName()` —— 它同时决定 `userData` 目录，
  改了会换目录、**丢全部配置与会话**。只改运行时显示用的 `spec.productName` 参数。
- **只在"中文语境"里替换产品名**：看上下文而不是字符串边界（这些 bundle 是单行压缩的，
  正则/词法扫描都会因正则字面量、`${}` 嵌套而错位 —— 实测 setup-wizard 里几十条中文文案
  只能识别出 1 条）。于是英文段（`DSH Desktop Recovery Assistant`）和代码标识符
  （`data-dsh-boot`、`DESKTOP_RECOVERY_RESTART_PATH`）都不会被碰到。
- 通用标点（`…` `—`）**不算**中文语境 —— 否则 `Downloading DSH Desktop ${v}…` 这种英文串会被误伤。
- 改完立刻 `node --check` 语法自检。

## 三、怎么改 / 怎么退

| 想改什么 | 怎么做 |
|---|---|
| 任意界面文案 | `gen-client.mjs` → `TEXT_OVERRIDES`（精确）或 `TERM_MAP`（术语）→ `node gen-client.mjs` |
| 品牌名 | 只改 `BRAND.name` 一处，侧边栏 / 浮层 / 窗口标题同步 |
| 换 logo | `python 生成品牌图标内联.py <透明图> --preview 预览.png` → `node gen-client.mjs` |
| 全撤销插件层 | 删掉 `apply()` 里的 `installTextOverrides(ctx)` / `installTitleBrand()` 两行 |
| 全撤销 app 层 | `python 品牌文案补丁.py revert` |
| 撤销快捷方式改名 | `python 改快捷方式名.py revert` |
| 预演 app 层会改什么 | `python 品牌文案补丁.py`（不带 `--write` 就是 dry-run） |

## 四、明确不建议动

| 项 | 原因 |
|---|---|
| `app.setName(PRODUCT_NAME)` / 进程名 / exe 内嵌资源 | 会改变 `userData` 目录 → **丢配置与会话**；exe 还有签名问题 |
| `~/.dsh` 目录名、profile id | 同上，动了等于换一套环境 |
| 侧边栏插件注入列表 `dsh-finance-tools` 等工具名 | 是模型侧的能力标识，改了会破坏调用 |
| 主进程注入的插件加载失败提示（`src-*.js` 里那段多行 JS 字符串） | 改它有破坏代码的风险，且仅在插件加载失败时出现 |
